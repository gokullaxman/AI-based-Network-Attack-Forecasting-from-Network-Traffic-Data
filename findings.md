# Phase 6 Findings: Pipeline & AI Inference Validation Audit

## 1. Current 12 Input Features (Exact Order & Schema)
1. `conn_frequency` (flows/sec)
2. `packet_rate` (packets/sec)
3. `dst_ip_fanout` (distinct destination IPs)
4. `src_dst_entropy` (Shannon entropy of destination IP distribution)
5. `port_diversity` (distinct destination ports)
6. `well_known_port_ratio` (fraction of destination ports < 1024)
7. `host_sweep_rate` (distinct destination IPs / second)
8. `icmp_arp_ratio` (fraction of ICMP or ARP packets in window)
9. `service_probe_rate` (TCP SYN packets / second)
10. `targeted_query_volume` (average packet byte length in window)
11. `iat_jitter` (standard deviation of packet inter-arrival times in seconds)
12. `burstiness_index` (ratio of instantaneous packet rate to connection frequency)

## 2. Training vs Inference Pipeline Divergence
- **Origin of `scaler.pkl`**:
  - `scaler.pkl` was fitted in `train.py` on the output of `build_temporal_dataset()` (`pipeline/dataset.py`).
  - `build_temporal_dataset()` samples from synthetic Gaussian distributions defined in `STAGE_PROFILES`.
  - The mean and scale parameters in `scaler.pkl` match the synthetic profiles:
    - Mean: `[13.24, 95.18, 5.84, 0.41, 11.31, 0.71, 3.51, 0.165, 2.85, 50.23, 0.76, 4.17]`
    - Scale: `[12.06, 111.64, 5.71, 0.28, 17.66, 0.23, 5.12, 0.27, 3.08, 52.25, 0.45, 2.62]`
  - Real network traffic (e.g. idle traffic or standard web browsing) has radically different distributions (e.g. `iat_jitter` is in fractions of seconds, `packet_rate` can be 1-5 pkts/sec, `conn_frequency` is 0.1-2 flows/sec).
- **Origin of Model Weights (`bilstm_weights.pt`)**:
  - The model was trained for 15 epochs on 300 synthetic timelines generated by sampling Gaussian noise around hardcoded stage profiles.
  - The model has never been trained or evaluated on genuine network traffic, real PCAPs, or authentic CICIDS flow records.
- **Model Output Classes**:
  - Classes: `['Reconnaissance', 'Scanning', 'Enumeration', 'Exploitation', 'Intrusion']` (5 classes).
  - Head 1: Current stage classifier (`curr_stage_head`).
  - Head 2: Next stage forecaster (`next_stage_head`).
  - Target labels during training were created by advancing the fixed sequence `Reconnaissance -> Scanning -> Enumeration -> Exploitation -> Intrusion` deterministically! Thus, Head 2 was simply trained to predict `(current_stage_idx + 1)`. It is not an actual empirical forecast learned from real temporal attack transitions.

## 3. Flow and Sequence Construction Findings
- **In `pipeline/live_capture.py`**:
  - In `_process_genuine_packet()`, every 5 packets:
    `if self.actual_packets_captured % 5 == 0: recent_window = list(self.packets_buffer)[-5:]; self._aggregate_and_step_features(recent_window)`
  - Each step in `self.flow_sequence` is therefore an aggregate of the last 5 packets, regardless of IP 5-tuple, protocol, direction, or connection lifecycle!
  - 10 steps in `flow_sequence` therefore represent 50 captured packets (or 10 sliding 5-packet snapshots), NOT 10 independent bidirectional IP flows!
  - In `parse_pcap_bytes()`, chunks are sliced as `chunk_size = max(1, len(parsed_packets) // self.sequence_length)`. For a 37-packet PCAP, chunks are 3-4 packets each.
- **In `pipeline/real_flow_loader.py`**:
  - Reads CSV rows and computes features per row using heuristic formulas with hardcoded magic multipliers (e.g. `flow_pkts_sec / 10.0`, `tot_pkts * 10.0`, `dst_ports % 100`, `sweep_col * 5.0 + 0.2`).
  - If fewer than 10 rows exist, it repeats the first row (`np.tile(flow_features[0:1], (pad_count, 1))`).

## 4. Bandwidth vs Throughput
- In `dashboard/soc_manager.py`:
  `avg_pkt_size = (total_bytes / actual_packets) if actual_packets > 0 else 0.0`
  `bandwidth_kbps = round((pkt_rate * avg_pkt_size * 8) / 1024, 2)`
- This measures captured frame payload/header throughput at the packet sniffer layer, NOT physical wire bandwidth (which includes physical preamble, inter-frame gap, FCS, and framing overhead). It must be documented as "Captured Throughput" rather than "Physical Wire Bandwidth". Fixed in index.html to "CAPTURED THROUGHPUT" in kbps.

## 5. Phase 7A: Dataset Audit & Benchmark Evaluation Findings
- **Repository Datasets:**
  - `data/sample_cicids2017.csv`: 32 data rows. Contains no IP addresses, no timestamps, and 0 benign samples. Handcrafted synthetic toy file, not official CICIDS2017.
  - `data/sample_network_attack.pcap`: 37 packets generated via Scapy packet crafting. Synthetic test fixture.
  - Conclusion: Zero authentic benchmark records currently exist in the repository.
- **Candidate Benchmark Datasets:**
  - **CICIDS2017:** Recommended primary candidate. Provides official CICFlowMeter CSVs and raw PCAPs with authentic timestamps and benign/attack labels.
  - **CSE-CIC-IDS2018:** Recommended secondary / enterprise-scale candidate. Provides modern AWS infrastructure telemetry, but very large (~7 GB CSV / 400 GB PCAP).
  - **UNSW-NB15:** Strong alternative for Task A (detection), but traffic was generated using an IXIA traffic generator with concurrent synthetic bursts rather than an organic sequential kill chain.
- **Task Separation:**
  - **Task A (Benign vs Attack Detection):** Fully supported by CICIDS2017 flow data (binary classification or multi-class attack classification).
  - **Task B (Temporal Attack Forecasting):** Requires authentic chronological progression. Most CICIDS2017 attacks are isolated scheduled exercises (e.g., DoS on Wed, Brute Force on Tue). The Thursday Infiltration scenario is the only verified candidate featuring genuine progression (compromise -> discovery -> lateral scan). Mapping generic attack names to kill-chain stages without empirical transition evidence is scientifically invalid.
- **12-Feature Schema Mapping:**
  - Significant discrepancies exist between live packet window extraction (calculated across 5 packets) and flow CSV extraction (calculated per bidirectional flow summary).
  - In particular, `targeted_query_volume` in live mode measures average frame length, whereas in flow CSVs it is approximated from `Fwd Segment Size Avg`.
